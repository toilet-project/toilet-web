# 내 제보 서버 페이지 조회

웹 내 제보는 날짜·상태 조건에 맞는 이력을 10개씩 조회한다. 기존 회원 세션 갱신과 필수 동의 확인을 유지한다. 제보·시설·회원 데이터, DB 스키마, 시설 캐시를 변경하지 않는다.

## 조회 계약과 호환

- `GET /api/v1/reports/me/search?page=0&size=10`: 선택 상태와 날짜에 맞는 `items`, `page`, `size`, `totalElements`, `hasNext`, `statusCounts`를 반환한다.
- `from`·`to`는 KST 날짜이고 종료일 전체를 포함한다. 상태가 생략되면 전체 상태다. `statusCounts`는 날짜 조건에 맞는 각 상태와 전체의 건수여서 탭 숫자가 현재 페이지 크기로 줄어들지 않는다.
- 최신 생성 시각·제보 ID 내림차순으로 정렬한다. 페이지는 0부터 시작하며 요청당 1~50개만 허용한다. 필터·건수·상세의 본인은 JWT와 필수 동의 확인으로 결정한다.
- `GET /api/v1/reports/me/{id}`: 로그인한 본인의 한 건만 조회한다. 없는 제보·타인의 제보는 같은 404 응답이다. 알림 대상이 오래되어도 중간 페이지를 전부 읽지 않는다.
- 기존 `GET /api/v1/reports/me`의 배열 응답은 유지한다. 현재 모바일 앱과 구형 웹은 계속 이 경로를 쓴다. 모바일에 새 API를 적용하는 배포는 별도 작업이다.

## 화면 동작

날짜·상태가 바뀌면 페이지를 새로 조회하고 이전 응답은 반영하지 않는다. 더 보기와 자동 로딩이 겹쳐도 같은 페이지 요청을 중복 실행하지 않는다. 추가 조회 실패 시 이미 읽은 제보를 유지하고 실패한 페이지를 재시도한다. 알림 대상은 별도 조회한 카드로 먼저 펼쳐 보여주며 일반 목록에 같은 ID가 나타나면 중복 표시하지 않는다.

회원별 패널 재생성과 세션 만료 처리에서 이전 회원의 목록·상세를 지운다. 회원 이력을 공유 캐시에 저장하지 않는다. 데이터 저장이나 알림 읽음 처리는 조회 검증에 포함하지 않는다.

## 배포·검증 기준

API를 먼저 배포해 새 경로와 기존 배열 경로를 확인한 뒤 웹을 배포한다. 웹에서 새 API 오류를 기존 전체 조회로 자동 대체하지 않는다. 오류는 재시도 안내로 표시한다.

자동 검사로 실제 제한 JPQL 조회·날짜 경계·타인/비회원 제외·동일 시각 정렬·JWT 본인/동의 경계·기존 배열 호환과 더 보기 실패/재시도·필터/회원 전환의 늦은 응답·알림 단건 조회를 확인한다. 추가로 프리뷰·운영에서 기존 로그인 상태의 날짜·상태 숫자 및 상세를 비교한다.

DB는 건수 집계를 위해 본인의 해당 기간 이력을 읽는다. 반환·시설명 조회는 한 페이지로 제한하지만 DB 실행 계획이나 운영 성능 백분위의 개선까지 의미하지 않는다. 페이지 사이에 신규 제보가 추가되면 offset 경계가 이동할 수 있으므로 ID 중복을 제거하며, 새 항목은 필터 변경/재시도 시 다시 조회한다.
